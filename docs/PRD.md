# 周末有方 · 需求设计 v1

> 定位：大学生的周末城市探索指南
> 主张：**打开就有这周末能直接出发的方案，转发到群里就能定下来。**
> 方向：以「方案生成」为主干（A），在组队里嫁接「偏好合并」（B），打卡与分享借用「护照印章」视觉（C）。
> 约束：剩余开发时间 **4 小时**；纯静态部署；**部署域名不能变**。

## 1. 迭代路径总览（4 小时，每个里程碑结束都部署一次）

```
T+0:00 ─ M0 准备 ──────────── 0:20  拆分文件 / 新数据结构 / 扩充上海数据
T+0:20 ─ M1 方案引擎 ★ ──────── 1:20  首页方案卡 + 方案详情（时间轴、花费拆分、雨天备选）   → 部署 ①
T+1:20 ─ M2 组局 + 偏好合并 ★ ── 2:20  预置队伍 / 填写偏好 / 合并结果 / 重新生成方案 / AA → 部署 ②
T+2:20 ─ M3 打卡印章 + 攻略 ─── 3:05  按站打卡 / 印章动画 / 分享卡片 / 攻略一键套用      → 部署 ③
```

**原则：**
- 每个里程碑结束时，线上版本都必须比上一个版本更好，而且完整可用。即使中途停下，也不会留下半成品。
- ★ 是主路径必需的部分，优先级最高，进度落后时先砍其他部分（见 §8 砍需求线）。

## 4. 主路径：评审的 30 秒体验

**前提：** 首次打开时，**不需要任何操作就能看到结果**；预置了「305 宿舍周末局」，3 位室友已经填好偏好，只差“我”。

| 时间 | 评审看到 / 做什么 | 想传达的设计意图 |
|---|---|---|
| 0–3 秒 | 首屏：「上海 · 本周六 11/7 下午有雨（70%）」+「为你准备了 3 套方案」，第一张卡是“雨天也不湿鞋的文艺线 · 人均 ¥118 · 4 站” | 打开就有结果，天气直接影响推荐 |
| 3–10 秒 | 点开方案 → 时间轴：上午看展 → 地铁 18 分钟 → 午饭 → … 底部花费拆分：门票 ¥60 + 交通 ¥8 + 餐饮 ¥50 | 是可执行的行程，不是活动列表；预算算的是总花费 |
| 10–14 秒 | 看到某站标着「⚠️ 下午有雨」，点 [换成雨天备选]，户外站换成就近的室内站，总价同步更新 | 有 Plan B |
| 14–18 秒 | 点 [发到群里组局] → 进入局详情：3 位室友的偏好已填，“我”待填 | 组队直接承接方案，不用重新选 |
| 18–25 秒 | 用 10 秒填完自己的偏好 → 出现**合并结果**：「全员都有空：周六下午 · 预算按最低 ¥100 · 已避开：爬山（小林）、排队久（阿杰）」 | ★ 解决群里都说随便 |
| 25–30 秒 | 点 [按全员偏好重新生成] → 方案更新，并提示「替换了 1 站：佘山徒步 → M50 画廊（小林不想爬山）」，显示 AA 人均 | 决策可解释，可以直接定下来 |
| 加分 | 足迹 → 一键打卡 → **盖章动画** → 攻略 → 生成护照风分享卡片 | 闭环完整，有记忆点 |

**第二条路径（验证推荐是“真算”的）：** 把人数改成 1、预算拖到 0、切换到周日（晴），3 套方案会明显变化（例如出现“0 元梧桐 City Walk”“一个人的看展日”）。

## 5. 功能详细设计

### 5.1 方案生成引擎（P0 ★）

**输入：** `Prefs = { city, day, people, budget, likes[], avoid[], slots? }` + 当天分时段天气

**时段：**

| key | 时间 | 说明 |
|---|---|---|
| `am` | 09:30–12:00 | 上午活动 |
| `lunch` | 12:00–13:30 | 午饭（food 类，没有就用“附近简餐 ¥35”） |
| `pm` | 13:30–17:30 | 下午活动 |
| `dinner` | 17:30–19:00 | 晚饭 |
| `eve` | 19:00–22:00 | 晚上活动（可选） |

**主题模板**（每个模板是一组时段 + 类型偏好）：

| 主题 | 骨架 | 触发 / 加权条件 |
|---|---|---|
| 雨天文艺线 | am 室内展 → lunch → pm 室内展/市集 → eve 演出 | 任一时段降雨概率 ≥ 60% 时加权 |
| 0 元穷游线 | am City Walk/免费展 → lunch（便宜） → pm 免费市集/Walk | 预算 ≤ 50 时加权 |
| 户外放风线 | am 徒步 → lunch → pm City Walk | 晴天时加权；下雨时降权 |
| 多人热闹局 | pm 演出/剧本杀 → dinner → eve 夜市/夜骑 | 人数 ≥ 4 时加权 |
| 一人治愈线 | am 展览 → lunch → pm City Walk | 人数 = 1 时加权 |

**算法：**
1. 先按 `avoid` 做硬过滤（例如 爬山 → 去掉 `type=hike`；排队久 → 去掉 `queue=true`；户外 → 去掉 `indoor=false`）。
2. 每个模板的每个时段，从候选活动里贪心选得分最高的一个；**和上一站同区或距离近的加分**。
3. 计算交通段和花费，得到方案总分 = 各站平均分 + 预算吻合度 + 主题与天气、人数的吻合度。
4. 取得分前 3 的**不同主题**，生成标题和标签（`雨天友好` `0元` `适合4人` `需预约`）。

**单站得分（沿用 demo 的逻辑并加深）：**
- 兴趣命中 +40，否则 +10
- 天气：该时段下雨时，室内 +25、户外 −10 并标 ⚠️；晴天时户外 +25、室内 +15
- 人数：在 `[min, max]` 区间内 +15；正好等于 `best` 再 +5
- 学生优惠 +5

**交通段：** 用区域坐标估算距离 `d`（公里）
- `d < 1.5`：步行，`d × 12` 分钟，¥0
- `d < 5`：骑行，`d × 5 + 3` 分钟，¥1.5
- 其他：地铁，`10 + d × 2.5` 分钟，`¥3 + ⌊d / 10⌋`

**花费（按人均）：** 门票 + 交通 + 餐饮 = 合计；和预算比较后显示进度条（绿 / 黄 / 红）。

### 5.2 方案详情（P0）
- 竖向时间轴：每站显示时间、名称、类型 emoji、室内/户外、人均、来源标签（豆瓣同城 / 大麦 / 小红书 / 公众号）
- 站与站之间：🚇 地铁 18 分钟 · ¥4
- 户外站遇到降雨时段：显示 ⚠️ 和 [换成雨天备选]（取同时段、最近的室内活动）
- 每站有 [换一个]：同时段换成次优候选，总价实时重算
- 推荐理由：天气、预算、人数、兴趣各一句
- 底部固定 CTA：**[发到群里组局]**（主按钮）/ [我自己去]

### 5.3 组局 + 偏好合并（P0 ★）

**偏好问卷（10 秒填完，4 个问题）：**
1. 什么时候有空：周六 上午/下午/晚上，周日 上午/下午/晚上（多选）
2. 预算上限：滑杆
3. 想玩：类型多选
4. 不想要：爬山 / 排队久 / 太远（单程 > 40 分钟）/ 户外 / 太早起（多选）

**合并规则：**

| 维度 | 规则 | 理由 |
|---|---|---|
| 时段 | 取交集；交集为空时，选覆盖人数最多的时段，并标出谁不能来 | 时间对不上是组局失败的第一原因 |
| 预算 | 取所有人的**最小值** | 不能让最穷的人为难 |
| 兴趣 | 按票数加权（3 人想看展 > 1 人想徒步） | 照顾多数 |
| 不想要 | 取**并集**，作为硬过滤 | 一票否决，避免有人勉强参加 |

**合并结果文案示例：**
> 全员都有空：**周六下午** · 预算按最低 **¥100** · 3/4 人想**看展** · 已避开：爬山（小林）、排队久（阿杰）

点 [按全员偏好重新生成] 后：方案限定在交集时段内，并显示差异：「替换了 1 站：佘山轻徒步 → M50 画廊（小林不想爬山）」。

**预置演示队伍「305 宿舍周末局」：**

| 成员 | 有空时段 | 预算 | 想玩 | 不想要 |
|---|---|---|---|---|
| 小林 | 周六下午、周六晚上、周日下午 | ¥150 | 展览、美食 | 爬山 |
| 阿杰 | 周六下午、周日全天 | ¥100 | 演出、美食 | 排队久 |
| Mia | 周六上午、周六下午 | ¥200 | 展览、市集、City Walk | — |
| 我 | **待填写** | | | |

**其他内容：** 集合地点和时间（取方案第一站）、AA 人均与总额、天气提醒、[复制邀请文案]（包含邀请码和 `#join/CODE` 链接）、[确认出发] → 方案进入足迹页的“进行中”。

> 取舍：不做真实的多人同步。邀请链接只是让打开的人进入填写页；本地演示依靠预置队伍。设计说明里写明“正式版接入后端后实现实时同步”。

### 5.4 打卡印章（P0）
- 足迹页顶部是“进行中的方案”，按站列出，显示 [打卡] 和进度（2/4）
- 打卡浮层：星级、实际花费、一句话、照片（压缩到 160px）
- 完成后显示**盖章动画**：圆形印章，包含类型 emoji、站名缩写和日期，旋转 −12°，从 1.6 倍缩放落下
- 城市护照：按类型分格的印章墙 + 统计（足迹数 / 玩过的类型 / 累计花费）+ 徽章
- 也保留手动打卡（不在方案里的地点）

### 5.5 攻略与分享（P0 / P1）
- [生成我的攻略]：用已完成的方案和打卡记录自动生成标题、分站点评、总花费和标签，可以编辑后发布到同城攻略流（P0）
- 分享卡片：护照风格的竖版卡片，包含城市印章、路线、花费、星级和产品名（P1，先做 DOM 卡片 + 复制文案；有余力再用 Canvas 导出图片）
- 同城攻略流：最热 / 最新、点赞、**[一键套用这条路线]** → 生成方案并跳到首页（P0，这是闭环的最后一环）

### 5.6 设计说明（P1）
- **桌面（宽度 ≥ 1024px）：** 左栏是说明面板，右栏是手机框（390×844）里的应用。评审大多会用电脑打开，这样不打断使用流程，也能看到产品思考
  - 一句话主张
  - 痛点与功能对照表（4 行）
  - 「体验 3 步」：点击后右侧应用跳到对应位置
  - [重置演示数据]
- **手机：** 顶栏 ⓘ 打开同样内容的浮层

## 6. 数据结构

```js
// ---- 静态数据（js/data.js）----
City = { id:'sh', name:'上海',
  areas: { '徐汇滨江':[2,3], '长宁':[0,4], ... } }       // 示意坐标，单位 km，用于估算交通

Weather = { sh: [ /* 0=周六, 1=周日 */
  { am:{w:'多云', i:'⛅', t:16, rain:20},
    pm:{w:'小雨', i:'🌧️', t:15, rain:70},
    eve:{w:'中雨', i:'🌧️', t:14, rain:80} }, ... ] }

Activity = {
  id:'sh1', city:'sh', name:'西岸美术馆 · 当代影像特展',
  type:'exhibit',            // exhibit|market|show|hike|walk|food
  indoor:true, area:'徐汇滨江', slots:['am','pm'], dur:2.5,
  price:60,                  // 人均门票或消费
  people:{min:1, max:6, best:2},
  queue:false, book:true,    // 是否排队久、是否需预约
  student:'学生票半价', source:'豆瓣同城', desc:'…'
}

Guide = { id, city, author, title, stops:['sh5','sh8','sh9'], cost, star,
          tags:[], likes, daysAgo, body }

// ---- 运行时（js/engine.js 计算产生）----
Prefs = { city, day, people, budget, likes:[], avoid:[], slots:null }

Plan = { id, city, day, theme, title, tags:[],
  stops:[ { aid, slot, start:'09:30', end:'12:00', locked:false, rainSwapped:false } ],
  legs:[ { mode:'地铁', min:18, cost:4 } ],          // legs.length = stops.length - 1
  cost:{ ticket, transport, food, total },            // 人均
  score, reasons:[] }

Merged = { slots:['sat_pm'], absent:{ sat_am:['阿杰'] }, budget:100,
           likes:{ exhibit:3, food:2 }, avoid:[{k:'hike', by:'小林'}], summary:'…' }

// ---- 持久化（localStorage 'weekend-v2'）----
State = {
  v:2, prefs:Prefs,
  activePlan:Plan|null,                       // 进行中的方案
  teams:[ { id, code, name, plan:Plan, status:'collecting'|'confirmed',
            members:[ { name, color, filled:true, pref:{ slots:[], budget, likes:[], avoid:[] } } ],
            meet:{ place, time } } ],
  checks:[ { id, planId?, aid?, name, type, city, area, star, cost, note, pic?, date, with:[] } ],
  guides:[ /* 我发布的 */ ], liked:[], onboarded:false
}
```

**本周末日期：** 根据 `new Date()` 计算即将到来的周六和周日；如果今天就是周六或周日，显示本周末。天气数据按“周六 / 周日”索引，不绑定具体日期，**任何一天打开都合理**。

**数据量：** 上海 20 个活动（展览 5 / 市集 3 / 演出 3 / 徒步 2 / City Walk 3 / 美食 4），北京、杭州各 10 个；攻略每城 3 篇。

## 7. 功能取舍

| 做 | 理由 |
|---|---|
| 方案化推荐（行程 + 交通 + 花费拆分） | 直接降低决策成本，是本产品的主张 |
| 分时段天气 + 雨天备选 | 题目点名“天气”，demo 里只是一个布尔值 |
| 偏好合并（预置队伍演示） | 最有记忆点，解决最痛的群体决策问题 |
| 盖章打卡 + 护照 | 补足情绪价值和视觉记忆点，成本低 |
| 攻略一键套用为方案 | 补上闭环最后一环，体现产品结构 |
| 桌面双栏设计说明 | 评审多用电脑打开；考的是产品设计，把思考过程呈现出来本身是得分点 |
| 重置演示数据 | 保证评审和你自己每次都能走完整的主路径 |

| 不做 | 理由 |
|---|---|
| 真实后端 / 登录 / 多人实时同步 | 评审只有一个人，体验不到；4 小时内风险太高。在说明里写明“正式版方案” |
| 地图 SDK | 需要 key，评审的网络环境下可能加载失败；用区域示意 + 交通时长代替 |
| 实时天气 API | 外部依赖有失败风险，而且活动数据本来就是 mock，混用反而不一致 |
| 在前端调用大模型 | 静态页面会暴露 API key |
| 陌生人搭子匹配 | 冷启动和安全问题，与“纠结去哪玩”关系弱 |
| 购票 / 支付 | 只标注“需预约”和“学生优惠” |
| 第三方 CDN 库 | 一律不引入，避免评审打开时白屏 |
| 可选（P2，有余力再做）：一句话输入“4个人 下雨 100以内 想看展” → 按关键词规则解析成条件 | 有“智能感”，成本约 20 分钟 |
